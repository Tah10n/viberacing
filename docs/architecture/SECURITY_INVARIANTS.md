# Security invariants

These invariants are public design commitments. Each implementation must map them to an owner, an
enforcement point, and automated negative tests.

| ID             | Invariant                                                                                                                                                                                                                                                            | Primary owner                                        | Minimum verification                                                                                                                                                                                                |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| VR-PUBLIC-001  | Every tracked artifact is safe for immediate public disclosure and contains no secret, personal data, private log, or local path.                                                                                                                                    | Repository and CI                                    | Secret scanning, privacy-pattern scan, staged-diff review, synthetic-fixture checks                                                                                                                                 |
| VR-TRUST-001   | Community usage is always labeled as self-reported and never grants money, prizes, authorization, or valuable privileges.                                                                                                                                            | Product and Web                                      | Copy assertions, policy tests, no reward integration                                                                                                                                                                |
| VR-TRUST-002   | Verified league accepts no records until a server-verifiable OpenAI source is implemented, reviewed, and enabled server-side.                                                                                                                                        | Ingest and scoring                                   | Feature disabled by default; no client-set trust tier; negative API tests                                                                                                                                           |
| VR-CODEX-001   | The connector uses local stdio and a stable, allowlisted Codex App Server surface only.                                                                                                                                                                              | Connector                                            | Fixed handshake/account/usage/supervisor/admission/diagnostic tests; candidate manifest and matrix checks                                                                                                           |
| VR-CODEX-002   | Prompts, conversations, repository contents, Codex credentials, API keys, and account email never leave the local machine.                                                                                                                                           | Connector                                            | Closed fields, discarded account values, exact sync vector, non-reflective output and redacted diagnostic-preview tests                                                                                             |
| VR-SOURCE-001  | A CodexSource is an opaque user-declared Community source; it is not represented as a cryptographically verified OpenAI account identity.                                                                                                                            | Product, Web, Ingest                                 | UI disclaimer, schema naming, no global ownership claim                                                                                                                                                             |
| VR-SOURCE-002  | Usage Sync provider and accounting revision are immutable server-owned source attribution reached through the verified device binding; the client cannot submit or relabel either value.                                                                             | Contracts, Ingest, and Database                      | Reject-provider schema tests, exact lookup/wrapper tests, immutable-column and least-privilege PostgreSQL integration                                                                                               |

| VR-DEVICE-001  | Every persistent device key is pending without authority or bound to exactly one source and can submit only for that source.                                                                                                                                         | Pairing and Ingest                                   | Pairing/request proof, binding, cleanup, replay, cross-source, revoke, and authorization tests                                                                                                                      |

| VR-AUTH-003    | A recovery code grants only short-lived, one-time replacement-passkey authority; a normal session exists only after exact WebAuthn registration.                                                                                                                     | Web/Auth and Database                                | PHC scrub, authority scope/expiry, rotation/start, completion/login, and replay tests                                                                                                                               |
| VR-INGEST-001  | The server validates every payload and computes dates, scores, ranks, trust tier, and season state; clients cannot set derived fields.                                                                                                                               | Ingest and Database                                  | Strict schemas, reject-unknown tests, constraints, stored-procedure tests                                                                                                                                           |

| VR-ABUSE-001   | Account/source count does not multiply score beyond the profile daily cap, request authority, or administrative privilege.                                                                                                                                           | Scoring and Ingest                                   | Aggregation, cap, quota, and source-storm tests                                                                                                                                                                     |

| VR-RELEASE-001 | Every connector binary is built from a protected revision and is signed, checksummed, SBOM-described, and provenance-attested.                                                                                                                                       | Release pipeline                                     | Independent package, signature, provenance, and lifecycle verification from a clean machine                                                                                                                         |
| VR-ADMIN-001   | Normal user sessions cannot become admin sessions; every privileged action requires separate policy, passkey step-up, reason, and audit event.                                                                                                                       | Admin/Auth                                           | Exact local Access RS256/issuer/audience/individual-member verification, injected full authorization/audit ordering, and synthetic narrow/widened PostgreSQL role separation; real passkey/host/sink still required |

## Proposed invariant amendments (non-authoritative)

[ADR 0068](../decisions/0068-multi-agent-token-leaderboard-and-mcp.md) and
[ADR 0069](../decisions/0069-thin-client-and-low-friction-onboarding.md) are Proposed. Outside the
narrow accepted ADR 0071–0073 slices, the proposals remain non-authoritative. They do not amend the
active table above. Implementations must continue to satisfy the active table until an ADR is
Accepted for each remaining slice and must satisfy the remaining review steps below. ADR 0071
activates VR-SOURCE-002 for the Codex attribution foundation, and ADR 0072 activates VR-TOKEN-001
for the direct Community token metric. If the broader proposals are accepted, focused changes would:

- generalize VR-TRUST-002 to an independent default-off Verified decision per reviewed provider and
  VR-SOURCE-001 to a provider-attributed but still opaque AgentSource beyond the currently admitted
  Codex pair;
- add VR-MCP-001 for optional pairing-bound MCP transport that carries an already-derived canonical
  total but is not a usage meter, and VR-PROVIDER-001 for minimal-scope server-side Verified
  ingestion;
- generalize VR-AUTH-001 and VR-SOURCE-001 to support anonymous identity only through ADR 0069's
  temporary bootstrap credential. That key would permit a restricted bootstrap session, exactly the
  first passkey, or GitHub upgrade while no passkey exists; either promotion would retire it
  atomically, and it would never grant restricted recovery or subsequent passkey registration. A
  server-clock 90-day ownership lease would be renewable only by a valid pre-expiry bootstrap
  session proof, never by ordinary sync. Expiry would hide the profile and pause every source,
  preserve only the two promotion proofs for a 30-day grace, and then require separate bounded
  Jobs-only system-expiry cleanup. Promotion during grace would not automatically unhide or resume.
  A GitHub-linked profile that has never activated a passkey would use a fresh same-ID,
  single-purpose first-passkey authority; monotonic completion would prevent GitHub from resetting
  passkey history or replacing recovery;
- add VR-CLIENT-001 for bounded mixed-content readers that emit only a canonical daily total, and
  VR-ENROLL-001 for two-key enrollment, proof-class-specific admission consumption, atomic
  one-profile/one-source/first-device creation, one credential-store-protected key with no
  plaintext-file or product export/copy workflow per independently revocable device authority,
  time-bounded anonymous ownership, terminal bootstrap retirement and cleanup, GitHub-collision
  denial without merge, and fresh passkey protection for every later source/device or sensitive
  action regardless of whether the profile remains anonymous or is GitHub-linked; the key contract
  does not claim hardware-backed non-exportability and treats a compromised user process as able to
  extract or use local material;
- amend VR-INGEST-001 for the future readers only after their focused accounting ADRs define one
  documented provider aggregate or documented disjoint components, cache/reasoning/thought
  treatment, and cumulative-snapshot deduplication. Initial backfill would use independent
  single-source/single-season requests so a previous-season grace race cannot quarantine
  current-season dates.

Implementations must continue to satisfy the active table until an ADR is Accepted, this document is
changed, negative tests land, and migration/rollback requirements are met.

## Change policy

Changing an invariant requires:

1. a public ADR describing the motivation and alternatives;
2. an updated threat model and abuse-case analysis;
3. explicit maintainer and security review;
4. updated negative tests before the behavior ships;
5. migration and rollback instructions where stored data or credentials are affected.

Production thresholds, secrets, personal incident details, and exploit data that would materially
increase active risk belong in private operational systems, not in this document.
