# Security invariants

These invariants are public design commitments. Each implementation must map them to an owner, an
enforcement point, and automated negative tests.

| ID             | Invariant                                                                                                                                          | Primary owner                                        | Minimum verification                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| VR-PUBLIC-001  | Every tracked artifact is safe for immediate public disclosure and contains no secret, personal data, private log, or local path.                  | Repository and CI                                    | Secret scanning, privacy-pattern scan, staged-diff review, synthetic-fixture checks                                              |
| VR-TRUST-001   | Community usage is always labeled as self-reported and never grants money, prizes, authorization, or valuable privileges.                          | Product and Web                                      | Copy assertions, policy tests, no reward integration                                                                             |
| VR-TRUST-002   | Verified league accepts no records until a server-verifiable OpenAI source is implemented, reviewed, and enabled server-side.                      | Ingest and scoring                                   | Feature disabled by default; no client-set trust tier; negative API tests                                                        |
| VR-CODEX-001   | The connector uses local stdio and a stable, allowlisted Codex App Server surface only.                                                            | Connector                                            | Fixed handshake/account/usage/supervisor tests; candidate manifest and matrix checks                                             |
| VR-CODEX-002   | Prompts, conversations, repository contents, Codex credentials, API keys, and account email never leave the local machine.                         | Connector                                            | Closed fields, discarded account values, exact sync vector, redacted diagnostics                                                 |
| VR-SOURCE-001  | A CodexSource is an opaque user-declared Community source; it is not represented as a cryptographically verified OpenAI account identity.          | Product, Web, Ingest                                 | UI disclaimer, schema naming, no global ownership claim                                                                          |
| VR-DEVICE-001  | Every persistent device key is pending without authority or bound to exactly one source and can submit only for that source.                       | Pairing and Ingest                                   | Pairing/request proof, binding, cleanup, replay, cross-source, revoke, and authorization tests                                   |
| VR-DEVICE-002  | Device credentials cannot edit security settings, issue invites, manage other devices, unlink sources, or delete profiles.                         | Web and Ingest                                       | Deny-by-default scope matrix and IDOR tests                                                                                      |
| VR-AUTH-001    | GitHub establishes profile identity; a fresh passkey step-up protects device approval, recovery changes, source reactivation/unlink, and deletion. | Web/Auth                                             | OAuth state and PKCE tests; WebAuthn origin, RP ID, challenge, and replay tests                                                  |
| VR-AUTH-002    | Passkey login and critical step-up retain exact credential provenance; revoke is terminal and removes its stale browser and pending authority.     | Web/Auth and Database                                | Credential/session binding, replay, rollback, revoke/login race, and last-key tests                                              |
| VR-AUTH-003    | A recovery code grants only short-lived, one-time replacement-passkey authority; a normal session exists only after exact WebAuthn registration.   | Web/Auth and Database                                | PHC scrub, authority scope/expiry, rotation/start, completion/login, and replay tests                                            |
| VR-INGEST-001  | The server validates every payload and computes dates, scores, ranks, trust tier, and season state; clients cannot set derived fields.             | Ingest and Database                                  | Strict schemas, reject-unknown tests, constraints, stored-procedure tests                                                        |
| VR-INGEST-002  | Server receipt time controls deadlines and replay windows; untrusted client time cannot reopen or mutate a finalized season.                       | Ingest and Jobs                                      | Boundary-time tests and finalized-season immutability tests                                                                      |
| VR-ABUSE-001   | Account/source count does not multiply score beyond the profile daily cap, request authority, or administrative privilege.                         | Scoring and Ingest                                   | Aggregation, cap, quota, and source-storm tests                                                                                  |
| VR-CAR-001     | Car customization accepts only a bounded enum-based CarRecipe built from reviewed project assets; device and agent proposals never activate it.    | Agent Skill, Contracts, Web, Connector, and Database | Skill drift/injection checks, URL/file/markup rejection, signed proposal scope, browser-decision, and deterministic render tests |
| VR-ORIGIN-001  | Railway accepts public traffic only when it carries a fresh, body-bound proof from the configured Cloudflare edge.                                 | Edge and Services                                    | Direct-origin, atomic replay-race, body-tamper, and clock-skew tests                                                             |
| VR-DATA-001    | Auth, usage, audit, and migration capabilities use separate least-privileged database roles; runtime roles do not own schema objects.              | Database                                             | Privilege matrix integration tests and per-checkout adapter probes                                                               |
| VR-DELETE-001  | Confirmed deletion immediately hides the profile and revokes devices, then purges primary data within the documented window.                       | Web and Jobs                                         | End-to-end deletion, retry, backup-retention, and partial-failure tests                                                          |
| VR-CI-001      | Untrusted pull-request code never receives production, signing, release, or deployment credentials and cannot publish artifacts.                   | GitHub Actions                                       | Fork-PR tests, workflow permission audit, pinned-action policy                                                                   |
| VR-RELEASE-001 | Every connector binary is built from a protected revision and is signed, checksummed, SBOM-described, and provenance-attested.                     | Release pipeline                                     | Independent verification from a clean machine                                                                                    |
| VR-ADMIN-001   | Normal user sessions cannot become admin sessions; every privileged action requires separate policy, passkey step-up, reason, and audit event.     | Admin/Auth                                           | Role-separation and audit completeness tests                                                                                     |

## Change policy

Changing an invariant requires:

1. a public ADR describing the motivation and alternatives;
2. an updated threat model and abuse-case analysis;
3. explicit maintainer and security review;
4. updated negative tests before the behavior ships;
5. migration and rollback instructions where stored data or credentials are affected.

Production thresholds, secrets, personal incident details, and exploit data that would materially
increase active risk belong in private operational systems, not in this document.
